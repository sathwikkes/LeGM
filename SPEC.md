# Project: LeGM — Intelligent Fantasy NBA Draft Assistant

## Objective

Build a production-quality web application that assists a user during a live Yahoo Fantasy Basketball snake draft for a Head-to-Head Points league.

The application should function as a quantitative draft decision engine rather than simply an LLM-based recommendation chatbot.

The system must track every draft selection, maintain the set of available NBA players, understand every fantasy team's roster construction, calculate player value according to the league's exact scoring configuration, simulate future picks, and recommend the optimal players for the user's next selection.

The AI/LLM layer should explain and interrogate recommendations generated by deterministic analytics and simulation tools. The LLM should not independently calculate player rankings or projections.

## Technology

Frontend: Next.js + TypeScript

Backend: Python + FastAPI

Database: PostgreSQL

Cache/live state: Redis

Real-time communication: WebSockets

Analytics: Pandas, NumPy, SciPy, scikit-learn

ORM: SQLAlchemy

Validation: Pydantic

Optional AI framework: lightweight tool/function calling directly through the selected LLM SDK. Do not introduce LangChain unless orchestration complexity justifies it.

## League Configuration

Do not hard-code Yahoo scoring.

Represent each league using configurable settings including:

- number of teams
- snake or auction draft
- draft position
- roster slots
- bench slots
- injured-list slots
- eligible player positions
- scoring multipliers for every statistic
- acquisition settings when relevant

Example scoring configuration:

PTS = 1  
REB = 1.2  
AST = 1.5  
STL = 3  
BLK = 3  
TO = -1

The system must automatically recalculate player value whenever scoring configuration changes.

## Draft State Engine

Maintain an authoritative live DraftState containing:

current pick number  
current round  
current drafting team  
all completed picks  
all available players  
each fantasy team's roster  
each team's open positions  
user's next selection  
number of picks before user's next selection

Every draft action must be reversible using an Undo operation.

The application must never depend exclusively on an external fantasy-platform integration to maintain draft state.

## Draft Input Modes

Support manual pick entry as the guaranteed fallback.

Manual selection must be optimized for speed using fuzzy search and keyboard controls.

Architect adapter interfaces that could later support:

Yahoo Fantasy Sports API ingestion

or

a browser companion capable of detecting draft selections visible to the authenticated user.

External integrations must not be required for the recommendation engine to operate.

## Recommendation Engine

Generate a Draft Opportunity Score for every available player using configurable components including:

projected fantasy value  
VORP  
position scarcity  
roster fit  
expected games played  
injury risk  
projection uncertainty  
upside  
ADP value  
probability the player remains available at the user's next pick

Return both the final score and its component values so recommendations are explainable.

Avoid arbitrary black-box rankings.

## Probability of Return

Implement Monte Carlo draft simulations.

For each recommendation, estimate:

P(player survives until user's next pick)

Simulated opponents should consider:

ADP distributions  
ADP variance  
player rankings  
current roster construction  
position needs  
number of open roster slots

Run simulations asynchronously or cache results so recommendations remain responsive during a live draft.

The application should recognize situations where a slightly lower-ranked player should be selected now because a higher-ranked alternative is likely to remain available later.

## Roster Fit

Determine whether players can legally fill the user's remaining roster positions.

Calculate positional scarcity relative to the available player pool.

Penalize roster constructions that make future picks unnecessarily restrictive.

Eventually calculate projected usable fantasy points rather than only raw fantasy production by simulating daily NBA schedules and identifying points likely to remain on the fantasy bench because of lineup congestion.

## Opponent Modeling

Track every opponent's drafted roster.

Estimate likely position/player targets for teams selecting before the user's next pick.

Use opponent needs as one signal in the Monte Carlo simulation, but do not assume opponents always draft optimally.

## AI Agent

Expose deterministic backend tools to an LLM.

Example tools:

get_draft_state

get_my_roster

get_available_players

get_player_projection

get_player_value

compare_players

get_roster_needs

get_position_scarcity

simulate_until_next_pick

get_probability_of_return

get_opponent_rosters

get_injury_context

generate_ranked_recommendations

The LLM should use these tools to answer natural-language questions such as:

"Who should I draft?"

"Can I wait another round for a center?"

"Why are you recommending Player A over Player B?"

"Who is most likely to disappear before my next pick?"

"Which position is becoming scarce?"

"Give me the highest-upside pick."

"Ignore injury risk and compare these players."

Responses must distinguish objective model results from subjective strategic interpretation.

## Feedback System

Provide thumbs-up/down controls on recommendations.

Do not fine-tune the LLM directly from this feedback.

Store feedback and gradually learn user strategy preferences such as:

risk tolerance  
rookie preference  
upside preference  
injury aversion  
veteran preference  
ADP sensitivity

These preferences may adjust recommendation weights.

## Reliability

The live draft cannot depend on the LLM being available.

If the LLM API fails, quantitative recommendations must continue functioning.

If Yahoo integration fails, manual drafting must continue functioning.

If simulations are unavailable, basic VORP rankings must continue functioning.

Always maintain an authoritative local DraftState.

## Testing

probability simulations

Create deterministic mock drafts for integration testing.

The application should be able to simulate an entire fantasy draft automatically for development and benchmarking.

## Development Sequence

First implement the player database and scoring engine.

Then implement deterministic player rankings and VORP.

Then implement DraftState and a simulated snake draft.

Then create FastAPI endpoints.

Then build the Next.js draft interface.

Then implement Monte Carlo availability simulation.

Then add opponent modeling.

Then add the LLM tool-calling layer.

Then add Yahoo/browser integrations.

Never begin with the AI agent before the deterministic draft engine works.

## End Goal

The final application should behave like a fantasy basketball front office.

Instead of merely answering:

"Who is the best available player?"

it should answer:

"Given my scoring system, current roster, remaining player pool, draft position, opponents drafting before me, positional scarcity, expected availability at my next selection, injury risk, and projected fantasy production, which decision maximizes the expected value of my completed roster?"
